# low-context-writing（読者前提チェック）

一般書の校正者の視点で、「前提知識のない読者が、前を読み返さずに意味をたどれるか」を点検し、説明不足・前提知識への依存・論理の飛びを直すスキル。

AIが書いた下書きは要約しすぎて意味が飛びやすい。書き手の主張は変えずに、読者がつまずく箇所だけを補う。

## いつ使うか

- 技術記事（Qiita / Zenn / note）、提案書、README などを公開前に見直すとき
- 「読者目線で校正して」「前提知識なしで読めるか見て」と頼まれたとき
- AIが書いた下書きを仕上げるとき
- 自分で文章を書く・直すときも、この観点を常に当てる

## 点検する観点

1. **初出の専門用語・略語に説明があるか**
   - 例: RLSポリシー → RLS（データベースの行単位のアクセス制御）ポリシー
   - 例: p90、CRUD、LGTM、IaC、revert、approve など
2. **初出の人物・組織・製品に「何者か」の説明があるか**
   - 例: Flask作者 → PythonのWebフレームワークFlaskの作者
   - 例: CodeX → スタンフォード大学の法と技術の研究センターであるCodeX
3. **理由やつながりが省かれていないか**（「なぜそうするのか」が書いてあるか）
   - 例: 「機械学習のホールドアウトセットと同じ考え方である」
     → 「機械学習では、データの一部を学習に使わずに取っておき、最後の評価にだけ使う。これを『ホールドアウトセット』と呼ぶ。学習で見たデータで評価すると、答えを丸暗記しただけでも高得点になってしまうからだ。」
4. **1文に詰め込みすぎていないか**
   - 列挙・条件・結論が1文に入っていたら分ける
5. **指示語・番号・略称が、前を読み返さないと分からない形になっていないか**
   - 例: 「4を消した分、1・2・5を厚くしている」→「4（マージ前の承認）をなくした分、1（意図・仕様）・2（検証の設計）・5（事後の観測）を厚くしている」
6. **見出しや節の頭で、話題が急に変わっていないか**
   - 前の節とのつながりを1文で示す（例: 「以下、それぞれが人間の判断をどこへ移したのかを順に見ていく。」）
7. **唐突に固有の仕組み名から入っていないか**
   - 「目的 → 名前 → 中身」の順にする。見出しを仕組み名だけにせず、その節の論点が分かる形にする
8. **主語・目的語が抜けて、誰が何をするのか分からない文がないか**
   - 例: 「AI自身に監査させることで自動で修正をしてくれる」→「AI自身にコードを監査させれば、見つかった問題を自動で直してくれる」
9. **同じ言い回しが近くで重複していないか**
   - 例: 「性能がかなりあがっており」「性能は飛躍的にあがっており」が続く
10. **出どころが「名無し」になっていないか**
   - 「解説記事は」「ある調査では」「報告によると」のように、何の資料か分からない呼び方をしない。初出で媒体名・著者・どんな立場の資料かを書く
   - 例: 「解説記事は、成功の理由を〜としている」→「この仕組みを分析した技術ニュースレターのByteByteGoは、〜としている」
11. **箇条書きが因果や順序を隠していないか**
   - 項目どうしに「だから」「その結果」「そこで」の関係があるなら、箇条書きにせず地の文にする。箇条書きは、本当に並列な項目（変更点の一覧、比較の観点など）だけに使う
   - 例: 「実験した／レビューを後ろに移した／スキルを更新する／Symphonyを公開した」の4項目は、「人間のレビューが追いつかなくなった」という理由でつながっているので、段落にしてその理由を書く

## 守ること

- 書き手の主張・言い切りの強さ・文体（だ・である／です・ます）は変えない
- 説明を足すときは、確かな一般知識か出典にある内容だけにする。分からないことは推測で埋めず、書き手に確認する
- 説明は括弧で短く添えるのを基本にし、本文の流れを止めない
- 読者層に応じて足す量を調整する（Qiita読者が当然知る PR・Git などは説明不要）
- 点検の途中で事実の誤りに気づいたら、それも指摘する
- 書き手本人が書いた部分も、頼まれたら同じ基準で点検する

## 手順

点検は「意図の流れ」から先に行い、語句の説明はその後に行う。語句に説明を足しても、段落の流れが切れていれば読者は意図を追えないため。

1. 文章全体を通読し、想定読者（媒体・前提知識）を確認する
2. **流れの点検（節・段落単位）**
   - 各節について「この節は全体の主張の中で何を言うためにあるか」を1行で書けるか確かめる。書けない、または節の書き出しからそれが読み取れないなら、節の冒頭に1〜2文足す
   - 各段落について、読者として1文ずつ読み、文が終わるたびに「それは何？」「なぜ？」「だから何？」と問う。生まれた問いに次の文が答えていなければ、そこが飛びである
   - 新しい人物・組織・資料・仕組みが出てくる文は、「何者か」と「なぜここで出てくるか」が分かるかを確かめる
3. **語句の点検**：上の観点1〜11で、つまずく箇所を洗い出す
4. 修正案を作る
   - 語句の問題は、変わる部分だけの最小限の修正にする
   - 流れの問題（飛び・名無しの出どころ・因果を隠した箇条書き）は、段落単位で書き直してよい。その場合も主張と事実は変えず、足すのは理由・つながり・紹介だけにする
5. 事実に関わる補足は、出典や一般知識で確かめてから入れる
6. 書き直した段落を、もう一度ステップ2の問いで読み直す

## 出力

- 修正案は1か所ずつ「元の表現 → 修正案（理由）」で示す
- 編集できるドキュメントなら、修正案（提案モード）として本文に直接置き、書き手が1件ずつ採否を選べるようにする
- 最後に、直した観点ごとのまとめと、書き手に確認したい点（あれば最大2つ）を短く添える
